## CFG-R1 — PAY-001 state matrix runtime validation (2026-09-17)

Lock §6: "Run payment-gateway states B, C, D (with profile), F, [H] --
read the actual bound value at runtime -- to confirm the actual runtime
winner matches the expected column. The harness answer key must itself be
validated against the runtime, not against the docs." (harness §14.4 test 1
names B, C, D, F; harness §14.6 W1 adds state H; state G is not run --
see `targets/payments/payment-gateway/overlays/README.md`: an unreferenced
Helm `values.yaml` key has no runtime effect by construction.)

**Tool versions used (no harness-pinned JDK/Spring Boot build exists yet --
see `ecdat/docs/open-issues.md` OI-002 for the equivalent PRV-T1-3 gap; same
situation here, recorded rather than guessed):**
- JDK: `openjdk version "25.0.3" 2026-04-21 LTS`, `OpenJDK Runtime Environment Corretto-25.0.3.9.1 (build 25.0.3+9-LTS)`
- Maven: `Apache Maven 3.9.16 (2bdd9fddda4b155ebf8000e807eb73fd829a51d5)` -- downloaded directly from `https://dlcdn.apache.org/maven/maven-3/3.9.16/binaries/apache-maven-3.9.16-bin.zip` (version confirmed via Apache's own directory listing, not memory) because neither Maven nor Docker is installed on this machine
- Spring Boot: `4.1.1` (latest stable per `repo1.maven.org` `spring-boot-starter-parent` `maven-metadata.xml` at fetch time, not memorised)

**Method:** `harness/eval/validate_cfg_r1.py` builds the real fixture at
`targets/payments/payment-gateway` with `mvn package`, then launches the
actual jar with `java -jar` under each state's real environment
variables/profile/CLI args/working directory, and reads the bound value from
a `CommandLineRunner` that logs `CFG-R1 pay.keywrap.transformation=<value>`
and exits (no HTTP server, no actuator needed -- this fixture has no
`spring-boot-starter-web` dependency; logging satisfies harness §14.4's
"log the bound value" instruction directly). Full raw JSON output:
`harness/eval/out/cfg_r1_results.json` (gitignored, regenerated by re-running
the script).

**Command:**
```bash
export PATH="<path-to-maven-3.9.16>/bin:$PATH"
python harness/eval/validate_cfg_r1.py
```

**Raw results (bound value actually logged by the running JVM, per state):**

| State | Real launch mechanism | Bound `pay.keywrap.transformation` |
|---|---|---|
| A | overlay `state-A/application.yml` (no `pay.keywrap` key at all), rebuilt, run with no args | `null` |
| B | base fixture, no overrides | `RSA/ECB/OAEPWithSHA-256AndMGF1Padding` |
| C | env `PAY_KEYWRAP_TRANSFORMATION=RSA/ECB/PKCS1Padding` | `RSA/ECB/PKCS1Padding` |
| D | env `SPRING_PROFILES_ACTIVE=prod` (uses committed `application-prod.yml`) | `RSA/ECB/PKCS1Padding` |
| E | env `SPRING_PROFILES_ACTIVE=prod` + `PAY_KEYWRAP_TRANSFORMATION=RSA/ECB/PKCS1Padding` | `RSA/ECB/PKCS1Padding` |
| F | CLI arg `--pay.keywrap.transformation=RSA/ECB/PKCS1Padding` | `RSA/ECB/PKCS1Padding` |
| G | not run (see method note above) | same as B (`RSA/ECB/OAEPWithSHA-256AndMGF1Padding`), by construction |
| H | run from a working dir with `./config/application.yml` = PKCS1 (base jar unchanged) | `RSA/ECB/PKCS1Padding` |

**Supports or contradicts the harness's assumed answer key:** SUPPORTS, for
every state actually run. All six real invocations (A, B, C, D, E, F) plus
the external-config test (H) produced exactly the value harness §14.3's
table expects for that state. Two specific claims this empirically confirms
rather than takes from Spring documentation alone (per CFG-R1's own stated
purpose, "validated against the runtime, not against the docs"):
- **State D:** a profile-specific file (`application-prod.yml`) really does
  override the non-specific `application.yml` once `SPRING_PROFILES_ACTIVE=prod`
  is set, on this exact Spring Boot 4.1.1 / JDK 25.0.3 build -- not merely
  claimed by the Spring reference docs cited in harness §14 CFG-001.
- **State H (harness §14.6 W1):** an external `./config/application.yml`
  really does override the packaged classpath `application.yml`, confirming
  W1's claim that "config data outside the jar overrides the packaged file
  (lower than env, higher than the repo yml)" -- at least relative to the
  repo yml; this run did not test it against an env-var override
  simultaneously, so the "lower than env" half of that ordering claim is
  still unverified here (state E already confirms env beats the *profile*
  yml, which is the closer analogue tested).

**Outstanding / not verified by this run:** whether the external
`config/application.yml` from W1 ranks correctly against `os-env` (5) —
would need a state combining both, not currently in the harness §14.3 table.
